# 第 2 期·步骤 4：基准标的与交易日历回补

> 状态：**待认可**。这是进入信号阶段前的两块补丁，都不新增外部依赖，改动集中在存储与作业。

## 1. 为什么做这两件

盘点行情底座时发现两个会在信号阶段立刻绊脚的缺口：

- **没有基准**。库里指数标的为零。相对强弱、超额收益、贝塔都要拿个基准比。
  标普这边持仓里的 SPY 可以顶上（20 年数据齐），纳指没有对应标的。
- **交易日历只有 54 天**（2026-07-06 至 09-18）。日常增量够用，因为每次都重拉前 60 天后 10 天；
  但按日历遍历历史的逻辑一律做不了，回测首当其冲。

## 2. 实测事实（决定方案的部分）

**交易日历取不到 20 年，最多约 10 年。** 对真实网关跑了四档区间：

| 请求区间 | 返回 |
| --- | --- |
| 2026 全年 | 251 天，2026-01-02 起 |
| 2021-01-01 起 6 年 | 1506 天，2021-01-04 起 |
| 2006-01-01 起 21 年 | **2591 天，2016-09-12 起** |
| 2000-01-01 起 27 年 | **2591 天，2016-09-12 起** |

请求 21 年和 27 年返回完全一样，说明 2016-09-12 是券商侧的硬边界，不是分页问题。
所以"日历回补到 20 年"这件事**做不到**，我之前的建议这一半要修正：券商能给的只有约 10 年。

**QQQ 券商认识**：id=203290，纳指 100 ETF，类型 4（Trust）。
顺带确认 IWM（罗素 2000）、DIA（道指）也都认识，将来要别的基准不用再试。

**历史额度够**：生产当前 58/100（7 天滚动），加一只 QQQ 拉 20 年只占 1 个。

## 3. 范围

| 做 | 不做 |
| --- | --- |
| 新增 `BENCHMARK` 角色，把 QQQ 作为纳指基准纳入采集 | 自动挑选基准、多基准组合 |
| 交易日历回补：券商侧 2016-09 至今一次拉完 | 硬造 2016 年之前的日历（券商没有） |
| 2016 年之前的日历**从已有日 K 线反推**，并标明来源 | 港股等其他市场日历 |
| 日历回补作业 + 覆盖视图 + 审计项 | 相对强弱、贝塔等指标计算（信号阶段） |

## 4. 基准标的

**新增角色而不是塞进 POOL。** QQQ 不是候选买入标的，混在 POOL 里，信号阶段"扫描池内标的找入场点"
会把基准当成候选，这类错误很隐蔽。SPY 情况不同，用户确实持有它，保持 HOLDING 不动。

迁移 V6：

```sql
ALTER TABLE pool_member DROP CONSTRAINT pool_member_role_check;
ALTER TABLE pool_member ADD CONSTRAINT pool_member_role_check
    CHECK (role IN ('POOL', 'HOLDING', 'BENCHMARK'));
```

- `PoolRole` 加 `BENCHMARK`；`UniverseScope.poolAndHoldings()` 语义不变（基准照样要深度回补、
  每日增量、实时订阅），另加 `benchmarks()` 供信号阶段排除。
- 池上限 `max-size` 只约束 POOL，基准与持仓不计入。
- 加入方式沿用现有接口：`POST /api/pool/QQQ?role=BENCHMARK`，自动建档 + 触发 20 年深度回补。
- 成本：历史额度 +1（58→59），实时订阅额度 +1（20→21，上限 100）。

## 5. 交易日历回补

新增作业 `CALENDAR_BACKFILL`，两段拼接：

1. **券商段**：一次 `requestTradeDate(2016-01-01 → 今天+10 天)`，实际回 2016-09-12 起约 2591 天，
   `kind` 用券商给的值，来源记 `FUTU`。
2. **反推段**：2016-09-12 之前，取 `daily_bar` 里**池 ∪ 持仓 ∪ 基准**（这些标的有 2006 年起的数据）
   出现过的所有 `trade_date` 并集。大盘股每个交易日都有成交，这个并集就是那段时间的交易日，来源记 `DERIVED`。
   反推段只补券商段没覆盖的日期，不覆盖券商数据。

表结构加一列（V6 同一迁移）：

```sql
ALTER TABLE trading_day ADD COLUMN source varchar(8) NOT NULL DEFAULT 'FUTU'
    CHECK (source IN ('FUTU', 'DERIVED'));
COMMENT ON COLUMN trading_day.source IS 'FUTU=券商给的（2016-09 起）；DERIVED=从日 K 线反推（更早，券商取不到）';
```

`upsertAll` 改为不覆盖已有的 `FUTU` 行，避免每日增量把反推段刷掉。

- 触发：手工 `POST /api/bars/calendar/backfill`；成分股周同步之后顺带跑一次（幂等，几秒）。
- 日常增量继续按现有逻辑刷前 60 天后 10 天，不受影响。

## 6. 接口与视图

| 方法与路径 | 说明 |
| --- | --- |
| `POST /api/bars/calendar/backfill` | 日历回补作业 |
| `GET /api/bars/calendar?from&to` | 交易日列表（带来源），默认最近一年 |

`GET /api/bars/coverage` 增加日历字段：最早、最晚、天数、券商段与反推段各多少。

## 7. 审计

`GET /api/bars/audit` 增加一项提示级检查 `calendarCoverage`：日历最早日期应不晚于池与持仓的最早 K 线日期，
否则说明反推段没跑或跑漏了。不设为关键项——日历不全不影响当日数据正确性。

## 8. 验收

- QQQ 进库、20 年日 K 与复权因子齐、每日增量把它算进去、实时订阅 21 只。
- 日历覆盖到 2006 年，券商段与反推段边界处不重不漏；随机抽 20 个反推日期与该日 K 线互相印证。
- 两套审计仍全过；日 K 线全历史前收连续性仍为 0 处不一致。
- 生产验证后再更新文档与坑表。
